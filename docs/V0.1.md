# agentlife v0.1 — the smallest slice that ends the manual restarts

> **SUPERSEDED 2026-10-04 by `DESIGN-REVISION-1.md` §8.** The first slice is now registry-based with a
> Hello consent at restore time. Kept as the dated record of the first proposal.


Follows `DESIGN.md` (§ numbers refer to it). **Proposal for CireSnave's approval of a small first
target. No code until the PM approves.** Evidence ref: OverMind `origin/main` `c6c8c1e`.

## Goal, in one sentence

After a Windows update and a logon, every lane in the roster is started, PM first, in staggered
batches, each verified alive, none duplicated, and CireSnave is told what started and what did not,
**without him starting anything by hand**.

## In v0.1

1. **`roster.json`** (schema: `ROSTER-SCHEMA.md`), hand-seeded once from the 15 live lanes.
2. **`agentlife restore [--dry-run] [--only …] [--batch N] [--delay S]`** (§2): PM alone in batch 0, then
   batches; per-batch liveness by the lane's own state file (§2.3); idempotence by pid+start time, never
   "something is in this cwd" (§2.4); halt after N failed batches; lock file against two runs.
3. **Launch through the installed `lane-restart host`** (`C:/Projects/.claude-hooks/lane-restart.exe host
   --role R -- claude …`, §4.5/§6), so the dev-channels dialog is answered by CireSnave's existing
   approval. Without this, restore recreates the manual work. `wt.exe`, `conhost.exe` fallback, the `;`
   check and the environment strip, as `lane-restart` does.
4. **`agentlife list`**: roster ⨝ process table, read-only.
5. **A report file** per run, and one `[NOTICE]` to the PM lane over the broker (the path `notify.rs`
   uses). Whether CireSnave also gets a toast is Q4; v0.1 ships the file and the PM notice only.
6. **A documented `schtasks` command** for the logon task (§2.1), run by a person once. No
   `install-task` subcommand yet.
7. **A network wait at logon** (`gh api rate_limit`, bounded): the approval fetch failure of
   2026-10-01 is the one measured way restore silently degrades.
8. **Hard guards, no consent machinery:** non-PM `bypassPermissions` refused; `channels` limited to
   `server:claude-peers`; `extra_args` empty; `cwd` must be under `C:/Projects`; names/roles match
   `[A-Za-z0-9_-]{1,64}`; `;` in any argv element refused before anything starts.

## Trust in v0.1 (a decision for CireSnave, not assumed)

Without Hello, `roster.json` is an ordinary user-writable file, so any agent running as this Windows user
could edit it and the next restore would start what it says. The hard guards (item 8 above) limit *what* it can ask
for (no non-PM bypass, no new channels or flags, nowhere outside `C:/Projects`) but not *which lanes* or
*which model*. Mitigation that costs no new dependency: each restore compares the roster with the one it
last ran and puts **every difference at the top of the report and in the PM notice**. That is detection,
not prevention, stated as such. The choice is: (a) accept this for v0.1 and add Hello signing in v0.2
(recommended: it ends the manual restarts sooner), or (b) make Hello signing part of v0.1 and wait for
the OverMind reuse decision.

## No dependency on the OverMind extraction

v0.1 launches via the `lane-restart host` *subcommand*, which already exists, and builds the `claude`
argv itself. It therefore does **not** wait for the `relaunch` extraction
(`OVERMIND-EXTRACTION-NOTE.md`). The price is a temporary copy of `valid_identifier`,
`first_unsafe_argument`, the allowlist and the argv shape, each with a test that fails if the copy
drifts from the documented shape. The copy is removed in migration phase 2 (§8). If the PM prefers one
copy from day one, v0.1 waits for that OverMind PR instead.

## Done means (acceptance, in order)

1. Unit tests for the planner, identity, guards and argv (§9.1), mutation-checked.
2. `fleet-sim` with 40 stand-in lanes including the chaos set (§9.3).
3. One real `restore` of a 2–3 lane stand-in roster through the real `wt.exe` launch path, logged in
   `docs/ACCEPTANCE.md` (§9.2). Includes a Task Scheduler launch, which is UNVERIFIED today (§2.1).
4. A real-claude canary lane (§9.4), once, with CireSnave aware.
5. Only then: the real roster, `--dry-run` first, then the logon task.

## Estimated size, and what it still does not solve

Roughly: roster parse + validation, planner, process/identity reads, launcher, liveness, report, `list`,
plus the stand-in binary. It does not solve work lost since a lane's last HANDOFF (§7), a restore fired
into a pending shutdown, or the dev-channels approval expiring 2027-03-19.
