kind: the launcher no longer lets synapsed-client start a bare synapsed at logon
---
`agentlife launcher` called `synapsed_client::Daemon::connect`, which STARTS `synapsed` when nothing answers. At logon the launcher ran before the daemon's own task, so it auto-spawned a daemon without `SYNAPSE_LAUNCHER_ROLES` and `SYNAPSE_LAUNCH_SENDERS`; the task's own daemon then exited on the held lock, and the launcher was refused on the launch routes (`forbidden: this role may not use the launch routes`, 30 s loop in `launcher.log`, 2026-11-21). The launcher now waits, logging every 30 s, until something accepts a connection at the address `synapsed.json` names, and only then connects; it never starts the daemon. Cause read from the PM's measurement (pid 19312 auto-spawned 04:50:47 by `agentlife.exe launcher`) and from the client source (`connect` spawns once nothing answers). Reboot case: the launcher's task and the daemon's task both start at logon in no fixed order; if the launcher is first it now waits (and keeps logging) until the daemon task has the daemon up, then connects, so the daemon always carries the task's environment. Test: waiting on an empty home creates nothing there (`spawn_daemon` always creates `synapsed-start.err` first). Not run against the real daemon; the manual `--clear` path is unchanged and still may start one.

Also: the launcher logs at start which `lane-restart` it will run (the one NEXT TO its own exe) and warns when its version differs from the launcher's. Why: on 2026-11-21 the PM replaced only `agentlife.exe` (0.30.81) in `~/.agentlife-launcher/bin`; the sibling `lane-restart.exe` there stayed 0.30.67, so a woken launchtest still got the old generic start prompt and no claim step (retest: first fetch +79.9 s, no ack at +93 s). The fix for that run is PM-side (copy the 0.30.81 `lane-restart.exe` into that `bin`).

And: the launcher log gains `cycle: decided signal <signal_id> attempt <n>` (the id ends with the mail's enqueue time, so the log timestamp minus it is the mail-to-decision wait) and `cycle: took N ms` for a cycle that decided something, to locate the ~75 s wake delay measured 2026-11-21 (enqueue 16:18:37Z, lane-restart start ~16:19:52Z; earlier run ~6 s). ROADMAP O16 records that making `lane-restart install` refresh the sibling is NOT built and needs a decision.

And (PM option B, ROADMAP O16): at start the launcher makes the `lane-restart` next to its own exe its own version: when they differ and the installed `.claude-hooks/lane-restart.exe` IS the launcher's version, it renames the old one to `lane-restart.exe.bak-<version>` (a held file moves aside), copies, reads both SHA-256 back, and puts the old file back on any failure; a source that is not the launcher's version is never copied. Every outcome is logged, a failure as `WARNING: lane-restart sibling NOT refreshed: <why>`. Tests (with two mutations tried: no copy, no version guard; both failed a test): a stale sibling is replaced and the old kept, a matching one is untouched, a mismatched source is refused, a held file (Windows share-mode 0) is reported. The held-file test was not mutated.


Rate cap and refusal log lines (PM decision 2026-11-21): the overall launcher spawn cap is 24 an hour (was 12) in both the launcher engine and `lane-restart start`'s own gate; the per-role cap stays 3. A `refused:rate` log line now ends with the counts (`role n/3, overall n/24`), so it says which cap tripped. A held start's `--json` answer gains `detail` (`held for memory: 3.1 GB free, floor 8 GB`; the same field carries any refusal's words), and the launcher logs it as `start refused: role=<r> ...`. Held-for-memory attempts never counted toward either cap (a 2026-11-21 reading that they did was wrong: 14 real spawns in the hour had reached the overall cap of 12). Tests: the rate text, the `detail` field, the overall constant.
